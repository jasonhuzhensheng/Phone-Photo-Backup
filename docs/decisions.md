## D005：通过 ImageCaptureCore 直连手机

- 日期：2026-11-07
- 状态：已采纳，扩展 D003（文件夹来源保留）
- 背景：用户反馈“程序看不到手机”，要求加上手机直连。
- 决策：用系统框架 ImageCaptureCore 发现 USB 设备并读取文件；引擎新增 `runStaged`，通过注入的取文件闭包把每个文件下载到备份目录内的暂存区，核对大小后计算 SHA-256，再沿用原有的跳过、冲突副本和清单规则排他发布。对支持 HEIF 的设备请求原始资源。已备份且大小一致的文件不再从手机读取。手机锁定或断开时备份暂停，恢复后重读文件列表继续。
- 原因：ImageCaptureCore 是 macOS 自带、“图像捕捉”同款的接口，同时支持 iPhone/iPad 和 PTP 模式的安卓手机，不需要第三方依赖或驱动；暂存在备份盘上可以用同卷重命名发布，避免二次写入；取文件闭包让设备逻辑可以用模拟设备测试。2026-11-07 开发自检意外用上了连接着的真机：读到 17,359 项、复制 403 个文件 0 错误，但备份在无人操作时自行停止；之后探测到该 iPhone 处于锁定（受限）状态，推测是自动锁屏导致连接中断，而原实现把断开当作停止。因此改为等待恢复，并让自检模式不再搜索手机。锁屏后自动继续尚未在真机上验证。
- 影响：不支持安卓 MTP（macOS 不提供）、只存于 iCloud 的照片和 Mac 上的照片图库。设备来源无法对源文件重读校验。同一路径在手机上被替换为大小完全相同的不同内容时，再次备份会被当作未变化跳过。真机流程只能人工验收。


## D006：手机文件先暂存到本机磁盘，再大块复制到备份盘

- 日期：2026-11-07
- 状态：已采纳，修改 D005 中“暂存在备份盘上”的做法
- 背景：用户反馈从 iPhone 备份到三星 T7（exFAT，USB 10 Gb/s）特别慢，实测只有约 1.9 MB/s。对比测试：同样 8 个文件，ImageCaptureCore 下载到内置 APFS 盘 35.6 MB/s，下载到 T7 只有 3.45 MB/s；直接写 T7 时 128 KB 小块 16 MB/s、8 MB 大块 700 MB/s。程序自身每个文件只用约 0.1 秒，CPU 约 2%。结论：macOS 往 exFAT 写小块数据极慢，而 ImageCaptureCore 正是小块写入。
- 决策：`runStaged` 把暂存区放到本机临时目录；暂存区与备份同卷时仍 fsync 后重命名，跨卷时用 `copyVerified` 以 8 MB 大块复制，边写边校验 SHA-256，fsync 后排他发布。
- 原因：避开 ImageCaptureCore 在 exFAT 上的小块写入；校验和发布规则不变。代价是跨卷时每个文件多一次本机磁盘写入（一次一个文件，用完即删）。
- 影响：真机实测（iPhone 16 Pro，USB 2.0 数据线，480 Mb/s）从约 1.9 MB/s 提高到约 14 MB/s（首次读取的新文件）。剩余瓶颈在手机端和 USB 2.0 数据线。手机自动锁屏时备份会暂停，备份期间应把自动锁定设为“永不”。


## D007：一键导入 Mac「照片」并由 iCloud 同步

- 日期：2026-11-07
- 状态：已采纳
- 背景：用户有十部旧 iPhone，新手机已经用了一段时间，希望一键把所有照片和视频合并到新手机，且不重复。
- 决策：用 PhotoKit 把备份导入系统「照片」图库，由用户自己的 iCloud 照片同步到新手机。去重分三层：同一次规划内按 SHA-256 去掉跨备份的相同文件；导入记录按 SHA-256 记住已处理的文件；图库中已有的项目（例如新手机拍的、已同步到 Mac 的）按文件名主干和拍摄时间识别。新增自动模式：接入手机即扫描、备份、导入，无需点击。设备备份文件夹改为按设备编号归属，避免同名手机共用文件夹时按大小误跳过。
- 原因：iPhone 不允许电脑写入相机胶卷，「照片」+ iCloud 照片是唯一能让照片在新手机上正常编辑、删除的批量途径。PhotoKit 不提供去重，图库中已有照片的内容哈希需要逐个下载原件才能计算，所以对图库采用元数据匹配；照片元数据常缺时区，因此容许整点偏差。
- 影响：图库匹配是启发式的：文件名不同的同一张照片（如被重命名、经聊天软件转发）会被再次导入，可在「照片」的“重复项”里合并；没有拍摄时间的文件一律导入，宁可重复也不漏。`.AAE` 编辑文件不导入，iPhone 上编辑过的照片会以原片（和单独的 `IMG_E` 编辑版，如果有）导入。应用为 ad-hoc 签名，每次重新构建后 macOS 可能要求重新授权访问「照片」。PhotoKit 导入无法自动化测试，需用户在自己的图库上验收。


## D008：备份前检查大视频和重复项，经「照片」删除到“最近删除”

- 日期：2026-11-07
- 状态：已采纳
- 背景：用户希望备份前先列出最占空间的视频和重复的照片、视频，决定是否删除，并要求删除的项目进入“最近删除”。
- 决策：手机来源备份前显示检查清单。重复项按内容判断：先按文件大小筛选候选，只把大小相同的文件从手机分块读出计算 SHA-256。删除不走 ImageCaptureCore，而是在备份之后经 PhotoKit 在 Mac「照片」中删除，由 iCloud 照片同步到手机。默认只删除备份经核对的项目；用户可选择不备份所选项目。匹配采用文件名主干 + 拍摄时间 2 秒内且唯一，否则不删并列出。已删项目写入导入记录，防止导入步骤放回。
- 原因：通过数据线删除 iPhone 文件是否进入“最近删除”无法在不删真实照片的情况下验证，且开着 iCloud 照片的 iPhone 通常不允许电脑删除；「照片」删除一定进入“最近删除”（30 天可恢复）。用户原本要求先删除再备份，改为“先决定、再备份、后删除”，避免未备份的视频被删。2026-11-07 补充：用户再次确认需要“先删除再备份”，于是作为第二个按钮加入；确认框会说明所选项目不会备份、其中多少项已有旧备份副本，以及 30 天内可从“最近删除”恢复。原来的“备份后删除”保留为默认按钮。
- 影响：删除只对与 Mac 同一 Apple ID 并开着 iCloud 照片的手机有效；其他手机（如不同账号的旧手机）的选择项会列为“在照片里找不到”，需在手机上手动删除。近似重复（连拍、不同分辨率）不在检查范围内，可用「照片」的“重复项”。删除流程未在真机和真实图库上验证。2026-11-07 补充：用户要求更大的预览图并能播放视频再决定。视频优先播放备份副本，否则用 `AVAssetResourceLoaderDelegate` 按播放器请求的字节范围从手机读取（ImageCaptureCore 的 `requestReadData`），而不是先下载整个文件：十几 GB 的 ProRes 视频先下载要几分钟。代价是码率高于 USB 实际速度的视频会边播边停。


## D009：在应用里浏览备份中的视频并移到废纸篓

- 日期：2026-11-07
- 状态：已采纳
- 背景：用户希望在备份程序里查看备份文件夹下的视频，按大小排列，能预览、能删除、能看子目录。
- 决策：新增独立窗口，扫描整个备份位置（多部手机的备份一起），左侧是带大小的文件夹树，右侧是视频列表。删除只移到废纸篓，并且要先确认；不修改备份清单。实况照片的短视频默认隐藏。
- 原因：备份是唯一副本时，移到废纸篓可以挽回误删。清单保持不变，因为引擎在副本缺失时会自然处理：手机备份会重新复制仍在手机上的视频；删除前核对备份时，缺失的副本不算已备份；导入「照片」时跳过不存在的文件。
- 影响（D009）：想彻底不要的视频，还需要在手机上删除（可以用备份前检查）；否则下次备份会复制回来。移到废纸篓不释放空间，要清倒废纸篓后才释放；外置盘的废纸篓在该盘上。


## D010：直接从手机导入「照片」，图库查重只读需要的文件名

- 日期：2026-11-07
- 状态：已采纳
- 背景：用户希望直接把手机里的照片和视频同步到 Mac「照片」，重复的不导入；同时发现大图库上读取图库索引要好几分钟。
- 决策：新增“直接导入这部手机（不备份）”。先用手机文件列表里的文件名和拍摄时间查图库，已有的不读手机；其余逐个下载到临时目录，再用文件内的拍摄时间和 SHA-256 复查后导入，导入后删除临时文件。导入记录增加手机文件记录（设备 + 路径 + 大小），再次运行不再读取已处理的文件。图库索引改为只读取拍摄时间，文件名只对时间吻合的项目读取。
- 原因：逐项读取 `PHAssetResource` 的原始文件名是主要耗时；拍摄时间随资源一起取回，很快。先按手机元数据跳过已有项目，可以少读大量数据。
- 影响：不留备份，原件只在手机和「照片」里；建议重要的手机仍先备份。手机报告的拍摄时间与「照片」不一致时，会多下载一次再判断，不会重复导入。没有备份位置时，导入记录放在应用支持目录，和备份位置里的记录分开。真机和真实图库上未验证。2026-11-08 补充：用户要求导入前先看大视频、删掉太大的再导入。直接导入前复用备份前的检查清单（同一开关控制）。所选项目一律不导入；已在「照片」里的经 PhotoKit 移到“最近删除”，不在的留在手机上（需用户自己在手机上删）。导入记录把所选项目记为已删除或已跳过，以后导入同一部手机也不会放回；实况照片只要选中照片或视频之一，就整项排除，因为在「照片」里删除会同时删掉两者。代价：被跳过的项目以后不能通过本应用再导入，除非删掉导入记录中的对应条目。


## D011：显示版本号，经 GitHub Releases 自动检查并一键更新

- 日期：2026-11-08
- 状态：已采纳
- 背景：用户要求客户端显示版本号，并能自动更新。
- 决策：版本号显示在主窗口标题旁（悬停显示构建号）。更新源用本仓库的 GitHub Releases（仓库公开，`releases/latest` 无需登录）。启动时每天最多检查一次（可在应用菜单关闭），菜单可手动检查；发现新版本时显示更新说明，用户点“安装并重启”才下载。下载后核对 SHA-256（GitHub 资源的 `digest`，否则用发布说明里的 `SHA-256:` 行），解压后核对包标识、版本号和代码签名，再由一个等待旧进程退出的 shell 脚本替换应用并重新打开；替换失败时放回旧版本。备份或导入进行中不能安装。发布用 `scripts/release.sh`。
- 原因：项目约定不引入第三方依赖，所以没有用 Sparkle；需要的功能（检查、校验、替换、重启）用系统工具（`ditto`、`codesign`）几十行即可完成。URLSession 下载的文件不带隔离属性，ad-hoc 签名的新版本可以直接打开。需要用户点击才安装，避免在没人看着时重启。
- 影响：没有 Sparkle 那样的 EdDSA 签名，更新的真实性依赖 HTTPS 和 GitHub 账号安全；以后有 Developer ID 后可以加上团队签名核对。应用所在文件夹不可写时只能打开发布页面手动下载。开发测试可用 `PPB_UPDATE_FEED`（本地 JSON）和 `PPB_UPDATE_AUTOINSTALL=1`。2026-11-08 用本地模拟发布做了端到端测试：2.9.0 在约 2 秒内被替换为 2.9.1 并自动重启，临时文件清理干净；测试中发现打开着的表单会让 macOS 拒绝退出，已改为先关闭表单，仍被拒绝时直接退出。
