## D005：通过 ImageCaptureCore 直连手机

- 日期：2026-11-07
- 状态：已采纳，扩展 D003（文件夹来源保留）
- 背景：用户反馈“程序看不到手机”，要求加上手机直连。
- 决策：用系统框架 ImageCaptureCore 发现 USB 设备并读取文件；引擎新增 `runStaged`，通过注入的取文件闭包把每个文件下载到备份目录内的暂存区，核对大小后计算 SHA-256，再沿用原有的跳过、冲突副本和清单规则排他发布。对支持 HEIF 的设备请求原始资源。已备份且大小一致的文件不再从手机读取。手机锁定或断开时备份暂停，恢复后重读文件列表继续。
- 原因：ImageCaptureCore 是 macOS 自带、“图像捕捉”同款的接口，同时支持 iPhone/iPad 和 PTP 模式的安卓手机，不需要第三方依赖或驱动；暂存在备份盘上可以用同卷重命名发布，避免二次写入；取文件闭包让设备逻辑可以用模拟设备测试。2026-11-07 开发自检意外用上了连接着的真机：读到 17,359 项、复制 403 个文件 0 错误，但备份在无人操作时自行停止；之后探测到该 iPhone 处于锁定（受限）状态，推测是自动锁屏导致连接中断，而原实现把断开当作停止。因此改为等待恢复，并让自检模式不再搜索手机。锁屏后自动继续尚未在真机上验证。
- 影响：不支持安卓 MTP（macOS 不提供）、只存于 iCloud 的照片和 Mac 上的照片图库。设备来源无法对源文件重读校验。同一路径在手机上被替换为大小完全相同的不同内容时，再次备份会被当作未变化跳过。真机流程只能人工验收。


## D006：一键导入 Mac「照片」并由 iCloud 同步

- 日期：2026-11-07
- 状态：已采纳
- 背景：用户有十部旧 iPhone，新手机已经用了一段时间，希望一键把所有照片和视频合并到新手机，且不重复。
- 决策：用 PhotoKit 把备份导入系统「照片」图库，由用户自己的 iCloud 照片同步到新手机。去重分三层：同一次规划内按 SHA-256 去掉跨备份的相同文件；导入记录按 SHA-256 记住已处理的文件；图库中已有的项目（例如新手机拍的、已同步到 Mac 的）按文件名主干和拍摄时间识别。新增自动模式：接入手机即扫描、备份、导入，无需点击。设备备份文件夹改为按设备编号归属，避免同名手机共用文件夹时按大小误跳过。
- 原因：iPhone 不允许电脑写入相机胶卷，「照片」+ iCloud 照片是唯一能让照片在新手机上正常编辑、删除的批量途径。PhotoKit 不提供去重，图库中已有照片的内容哈希需要逐个下载原件才能计算，所以对图库采用元数据匹配；照片元数据常缺时区，因此容许整点偏差。
- 影响：图库匹配是启发式的：文件名不同的同一张照片（如被重命名、经聊天软件转发）会被再次导入，可在「照片」的“重复项”里合并；没有拍摄时间的文件一律导入，宁可重复也不漏。`.AAE` 编辑文件不导入，iPhone 上编辑过的照片会以原片（和单独的 `IMG_E` 编辑版，如果有）导入。应用为 ad-hoc 签名，每次重新构建后 macOS 可能要求重新授权访问「照片」。PhotoKit 导入无法自动化测试，需用户在自己的图库上验收。
